Federation Inbox Verification

The ActivityPub inbox accepted activities from anyone. How the trust path is supposed to work, what was missing, and what now guards it.

01 Two different trust paths

The identity provider authenticates two kinds of caller, and they share nothing. A person arrives with a JWT their own IdP issued. A peer instance arrives with an HTTP Signature over the request, and proves itself by a key published in its actor document.

This distinction is the whole reason federation is not "accept more issuers". A remote user never presents a token here — their client talks to their own home server, and the two servers talk to each other.

02 The issue

POST /users/:username/inbox never verified anything. The handler took the request headers as _headers — underscore-prefixed, discarded — and the route in router.rs carried no middleware. Across all 799 lines of inbox.rs, the only occurrence of the word "signature" was that unused parameter name.

The crate had the verifier and used it elsewhere: on attachment fetches, on presence polling, on the e2ee endpoints. The single endpoint that mutates the social graph was the one that skipped it.

What an attacker could do

The handlers read the activity body at face value — handle_follow trusts body["actor"], and handle_accept trusts it before flipping a friendship to accepted. So an unauthenticated POST could:

  • Forge a friend request from any actor, local or remote.
  • Forge the acceptance of one. This is the worst of the three: a pending request becomes an accepted friendship with a DM conversation minted, without the remote user ever consenting. It bypasses consent, not just authentication.
  • Overwrite cached remote profiles through Update{Person}.
Root cause. Not a missing primitive — the verifier existed and worked. The inbox was simply never wired to it, and nothing in the type system or the router made that omission visible.

03 The three checks

Verification now runs before any state is touched. Each check stops something the previous one cannot.

  1. 1 verify_http_signature Parses the Signature header, reads the signer's public key from the actor document named by its keyId, and verifies the signature over POST /users/:slug/inbox. Establishes that some real actor signed this request.
  2. 2 verify_body_digest Confirms the signature covers the Digest header and that the body which arrived hashes to it. Establishes that the bytes being acted on are the bytes that were signed.
  3. 3 verify_actor_binding Requires the activity's actor to be the key that signed the request. Establishes that the signer is speaking for itself.

Why the digest needs its own check

verify_request rebuilds the signing string from header values. A valid signature therefore proves the sender signed the string digest: SHA-256=… — never that the body attached to the request hashes to it. Nothing in the signature reaches the body.

Why a valid signature is not enough

Check 1 proves a real actor signed the request. It does not prove that actor is the one the activity claims to speak for. Without check 3, any federated peer holding a valid key of its own could sign an Accept naming someone else as the actor — and the handlers, which read body["actor"] directly, would act on it.

Invariant. keyId minus its fragment must equal the activity's actor. Signing for yourself is the only thing the inbox accepts.

04 Caching the verifying key

Check 1 fetches the signer's actor document. Done naively that is one outbound HTTP request per inbound request, which is both slow and an amplification vector. The cache is shaped by one decision:

TTL is not the rotation mechanism. If expiry were the only way a rotated key got noticed, the TTL would have to be short enough to bound how long valid requests are rejected — which defeats the cache. Instead, a verification failure against a cached key triggers a refetch. The TTL then only bounds memory, and can be hours.

The rest of the hygiene

  • Entries are promoted only after a signature verifies against the key, never merely on a successful fetch. Every entry in the verified tier corresponds to a peer that proved possession.
  • Failures are cached too. keyId is attacker-chosen, so one pointing at a dead or slow host must cost one fetch, not one per request.
  • Both tiers are capped. An unbounded map keyed on attacker-controlled input is a memory exhaustion bug.
  • Parsed keys, not PEM strings — the cache skips key parsing per request as well as the fetch.
  • Keyed on the full keyId including its fragment, not the actor URL: an actor may publish more than one key, and the fragment is what the signature references.

05 The client underneath

The keyId is a full URL supplied by whoever sent the request, so every fetch above is an outbound request to an address an attacker picked. The client making them was reqwest::Client::new(): no timeout, ten redirects, and rebuilt per call so the connection pool was discarded each time. A host that accepted the connection and never answered pinned a task indefinitely.

The body cap is enforced as bytes arrive rather than by trusting Content-Length, which a hostile peer can simply omit. Peer URLs are also screened before the request is made: the scheme must be https, and the host must not resolve into loopback, private, link-local or carrier-grade-NAT space — the classic SSRF target being a cloud metadata endpoint.

Both rules relax for local development, derived from the issuer: an https issuer is treated as production, a plain-http one as the alice/bob dev pair that federates over localhost.

Known gap. The screen resolves DNS, then reqwest resolves again when it connects. A hostile resolver can answer differently for each — DNS rebinding. Closing that needs a connector pinned to the screened address; the current code blocks the direct attempt, not the race, and says so at the call site.

Still open

  • DNS rebinding, as above — needs a pinned connector.
  • Signer ≠ actor. The binding assumes the signing key belongs to the activity's actor, which holds for everything this project emits. Implementations using instance-actor delivery ("authorized fetch") sign with a key whose keyId differs from the actor; federating with those will need a documented exception rather than a quiet loosening.
  • End-to-end inbox tests. The three checks are unit tested; a test driving a real signed request through the route needs a database and a signing peer.
Transport lives in crates/federation-transport/ and is shared with the chat server, which will need the same inbox on the same primitives. Domain handling — which activity verbs a service accepts — stays in the service.
