01 — Project Overview

Built on open standards.
Owned by no one.

🐳

Self-Hostable

Every layer ships as a Docker image. Run your own identity provider, messaging backbone, or community server independently.

🌐

Federated

Instances communicate via ActivityPub — the same protocol powering Mastodon. No central authority required.

🆔

Portable Identity

Your identity (alice@idp.alice.com) is not tied to any chat server. Join any community without creating new accounts.

🔑

Open Auth Standards

OIDC/OAuth2 for authentication. Chat servers never store passwords — they only validate JWT tokens.

🔒

End-to-End Encrypted

Every DM and group conversation is encrypted with MLS (RFC 9420). Encryption happens in the client; the server stores ciphertext it cannot read.

📱

Per-Device Identity

Each device holds its own Ed25519 Device Root Key, attested by your IdP. A user is the set of their attested devices — revoke one without touching the rest.

🗝️

Recoverable History

A 24-word passphrase derives a History Archive Key. Past messages are re-encrypted under it and stored as an opaque server-side archive — restorable on a fresh device, unreadable by the server.

📡

HTTP Signatures

Inter-server trust uses cryptographic HTTP signatures. No shared secrets. Federation without compromise.

03 — Object Storage

Your files.
Your instance.

Each identity provider instance ships with its own RustFS object storage — an S3-compatible server written in Rust. Avatars and DM attachments are owned by the sender's instance. The object store sits on the private network: neither browsers nor peer instances ever talk to it directly.

AVATARS

Stored on the user's own IdP storage, served via a public URL — https://storage.idp.alice.com/avatars/{user_id}.jpg. No authentication required. Anyone can fetch it.

DM ATTACHMENTS

Sealed client-side with AES-256-GCM before upload — a fresh key per attachment, carried inside the MLS-encrypted message. The store holds ciphertext. Bob's browser fetches via a token-protected /blob URL; his IdP fetches the original from Alice's /content endpoint under HTTP Signature and streams the bytes on.

S3-COMPATIBLE API

Code targets the standard S3 API via aws-sdk-s3 for Rust. RustFS can be swapped for MinIO, Ceph, or any S3-compatible service with zero code changes — just change the endpoint URL.

Asset Ownership Model
Asset Type Storage Location Access Method
User avatar Sender's IdP RustFS instance Public URL — no auth
DM / group attachment Sender's IdP RustFS instance (private) AES-256-GCM sealed — streamed through the IdP
Channel attachments Chat server storage (future) TBD — with Layer 3
04 — Federation

Talk to anyone.
From any instance.

Without federation, alice@idp.alice.com and bob@idp.bob.com would be isolated silos. ActivityPub bridges them — the same W3C standard powering Mastodon.

WEBFINGER

Standard HTTP discovery endpoint. Given alice@idp.alice.com, Bob's server queries idp.alice.com/.well-known/webfinger to find Alice's inbox URL and public key.

HTTP SIGNATURES

When delivering activities between servers, each HTTP request is signed with a private key and verified with the sender's public key. No shared secrets required.

ACTOR MODEL

Remote users are stored locally as "actors" with their public key and inbox URL cached. Efficient message delivery without repeated discovery calls.

MLS OVER ACTIVITYPUB

Every MLS payload rides inside a Create{Note} with mediaType: application/mls and an mlsKind discriminator — commit, welcome or application. The server routes the envelope without parsing the opaque body.

BEST-EFFORT DELIVERY

Outbound activities are delivered inline on a spawned task, with no durable outbox. Recovery is per-activity: clients pull missed MLS commits with ?since=<epoch> on reconnect, cached actors re-fetch on TTL, and time-sensitive activities are allowed to drop.

Trust Architecture
Relationship Responsibility Technology
User → IdP User authenticates with a password, then an optional TOTP second factor OIDC / OAuth2
Device → IdP IdP signs each device's Device Root Key; the attestation travels in the MLS leaf credential Ed25519 + JWKS
User → Chat Server Chat server validates JWT issued by IdP (with Layer 3) JWT + JWKS
IdP → IdP Servers authenticate each other for activity delivery and attachment fetches HTTP Signatures
Device → Device Message content — neither IdP can read it, whichever one is compromised MLS (RFC 9420)
05 — Example Scenarios

See it in action.

A Alice sends a private message to Bob +

Alice and Bob are on different self-hosted identity providers, and their conversation is an MLS group. Neither server can read a word of it.

01Alice types a DM. Her client encrypts it as an MLS application message under the group's current epoch key — inside the browser, in openmls compiled to WebAssembly.
02The ciphertext goes to idp.alice.com. The server stores it as an opaque blob; no plaintext ever reaches it.
03idp.alice.com wraps the ciphertext in a Create{Note} with mediaType: application/mls and signs the HTTP request with its private key.
04It resolves Bob's inbox URL — from the remote_actors cache, or via WebFinger on idp.bob.com on a miss.
05The signed activity is delivered to Bob's inbox, best-effort on a spawned task.
06idp.bob.com verifies the HTTP signature against Alice's server's public key and appends the ciphertext to Bob's Redis stream.
07Each of Bob's devices picks it up over WebSocket and decrypts it locally with its own MLS state.
08Bob reads the message. Two servers handled it; neither could read it.
B Alice joins a chat server +

Planned — Layer 3 is specified but not built. Alice wants to join the gaming community at chat.gaming.com. She already has an account at idp.alice.com.

01Alice navigates to chat.gaming.com in her browser.
02chat.gaming.com redirects Alice to her configured IdP: idp.alice.com.
03Alice authenticates at idp.alice.com — password, then her TOTP second factor if enabled.
04idp.alice.com issues a signed JWT token containing Alice's identity and claims.
05Alice's client presents the JWT to chat.gaming.com.
06chat.gaming.com fetches idp.alice.com's public key via the JWKS endpoint and validates the JWT.
07A local user record is created using the (issuer, subject) pair as a unique key.
08Alice is granted access. Her roles are managed locally by the chat server.
C Alice adds Bob as a friend +

Alice knows Bob's identity: bob@idp.bob.com. She wants to add him as a friend across instances.

01Alice searches for bob@idp.bob.com in her client.
02idp.alice.com queries idp.bob.com/.well-known/webfinger to discover Bob's profile.
03idp.bob.com returns Bob's inbox URL and public key.
04idp.alice.com sends a Follow activity (ActivityPub) to Bob's inbox, signed with its private key.
05idp.bob.com verifies the signature and notifies Bob of the friend request.
06Bob accepts — idp.bob.com sends an Accept activity back to idp.alice.com.
07Both servers cache each other as remote actors.
08Alice and Bob are now friends and can exchange private DMs.
D Alice adds a second device +

A user is the set of their attested devices. Adding one is an ordinary MLS membership change — no master secret is copied between machines.

01Alice's new laptop generates its own Ed25519 Device Root Key. The private half never leaves the machine.
02She signs in; idp.alice.com issues an attestation over the public DRK, verifiable by anyone who fetches her IdP's JWKS.
03The laptop publishes a batch of KeyPackages to the key directory, each leaf credential carrying that attestation.
04Alice's phone claims one and issues an MLS Add commit for every conversation she is in.
05The Delivery Service appends each commit in epoch order, rejecting racing commits with 409 so the group's history stays linear.
06The laptop claims its Welcome messages and joins each group at the new epoch. Every other member ratchets forward.
07Alice enters her 24-word passphrase. Argon2id over it and her server-stored salt derives the History Archive Key.
08The laptop downloads the opaque archive and decrypts it locally. Past messages are back — and the server still cannot read them.
06 — Deployment

Deploy in minutes.
Own it forever.

compose.yaml — Identity Provider 
# Self-hosted Identity Provider
services:
  idp:
    image: ghcr.io/pina-i/identity-provider
    environment:
      DOMAIN: idp.alice.com
      STORAGE_ENDPOINT: http://rustfs:9000
      REDIS_URL: redis://redis:6379
    ports:
      - "443:8080"
    depends_on:
      - postgres
      - redis
      - rustfs

  redis:
    image: redis:7-alpine
    volumes:
      - redis-data:/data

  rustfs:
    image: rustfs/rustfs:latest
    ports:
      - "9000:9000"
    volumes:
      - fsdata:/data

  postgres:
    image: postgres:16
    volumes:
      - pgdata:/var/lib/postgresql/data

07 — Development Roadmap

Start simple.
Grow incrementally.

Phase 1 Identity provider — OIDC, JWT issuance, JWKS, user management Built IdP
Phase 2 Messaging backbone — friends, DMs, presence over Redis Built Social Graph
Phase 3 ActivityPub federation between IdP instances — WebFinger, HTTP Signatures Built Federation
Phase 4 Object storage — avatars and attachments on RustFS Built Storage Layer
Phase 5 Group conversations — members, roles, reactions, replies, attachments Built Conversations
Phase 6 End-to-end encryption — MLS (RFC 9420), per-device identity, history backup Built E2EE
Phase 7 Account security — email verification, TOTP 2FA, recovery codes Built Hardening
Phase 8 Chat servers — channels, voice rooms, JWT-only auth Planned Layer 3
Phase 9 Public instance, docs, contributor guide — and a license file, which neither repository has yet Planned Open Source
Key Insight

The Identity Provider (Phases 1–7) and the Chat Servers (Phase 8) are completely independent projects that can be developed in parallel by different contributors. The interface between them is a JWT token — nothing more. The same discipline applies one layer up: the web client shares an HTTP and WebSocket contract with the backend, not a dependency graph, and lives in its own repository.
