# Pina'i — End-to-End Encryption (MLS)

E2EE for all DMs and group conversations using **MLS (RFC 9420)**. The IdP
becomes a key directory + delivery service; it never sees plaintext message
content. User identity keys are generated client-side and never leave the
user's devices, so a malicious or compromised IdP cannot impersonate users
or read messages.

For the protocol-level explainer of MLS itself (TreeKEM, KeyPackages,
commits, epochs), see [`/e2ee-protocols-overview.md`](./e2ee-protocols-overview.md)
in the project root. This document is the integration spec.

---

## 1. Threat model

### What we protect against

| Threat | Mitigation |
|---|---|
| IdP operator reads message content (legal order, insider, breach) | MSK never leaves user devices; IdP only sees MLS ciphertext |
| IdP operator silently MITMs a new conversation | KeyPackages signed by user-controlled SSK, not by the IdP CA — server can't mint a fake credential |
| Peer IdP serves a forged KeyPackage for one of its users | First-contact TOFU + non-dismissible warning on identity-key change. Out-of-band fingerprint verification optional |
| Compromised device | Per-device leaves: revoke just that leaf; remaining devices trigger a group commit excluding it. Post-compromise security recovers within one commit cycle |
| Compromised IdP CA / database | IdP holds **no** identity-signing keys for users. CA-key compromise downgrades the IdP to "DoS-capable", not "impersonation-capable" |
| Replay / reorder / forging by transport | MLS application-message authentication + epoch ordering |
| Lost passphrase + lost all devices | Conversations are unrecoverable. **This is by design.** Users opt into a Recovery Key at registration if they want fallback |

### What we do **not** protect against (non-goals)

- **Metadata.** The IdP knows: who's in each group, when commits happen, message ordering, sender device per message. We do not implement sealed sender or anonymous credentials.
- **Traffic analysis.** Padded delivery, cover traffic, mixnets — out of scope.
- **Endpoint compromise.** If your laptop is fully owned, all bets are off — this is true for every E2EE system.
- **Forward-only secrecy.** We rely on MLS's PCS (post-compromise security after a Commit), not on per-message DH ratchets that purge state. A compromised device key is recovered from on the next Commit cycle, not instantly.
- **Cross-IdP plaintext fallback.** All conversations are E2EE. A peer IdP that doesn't speak MLS gracefully fails the conversation handshake.

### What the IdP can still see after E2EE

Server-visible: `conversation_id`, `conversation_members` (actor URIs), per-message `(sender_device_leaf, created_at, ordering)`, `reply_to_id`, attachment row metadata stripped to opaque blobs, ActivityPub envelope addressing.

Server-opaque: message content, reactions, edited content, file bytes, file names, file MIME types, conversation names (where set), typing indicators (already pub-sub-only), reaction counts.

## 2. Trust model

### Key hierarchy (per user)

```
                         Master Signing Key (MSK)
                       generated client-side at first device pairing
                       never leaves the user's devices
                                  │
                ┌─────────────────┼─────────────────────┐
                ▼                 ▼                     ▼
       Self-Signing Key      User-Signing Key      Recovery Key
       (SSK)                  (USK)                 (opt-in,
       signs this user's      signs other users'    Argon2id-derived
       device leaf keys       MSK fingerprints      passphrase wraps MSK,
       and KeyPackages        when verified         blob stored on IdP)

                ▼
       Per-device leaf keys
       (one per paired device:
        web, desktop, …)
```

- **MSK**: Ed25519 (or alternative AEAD-friendly signature scheme). Root of the user's cryptographic identity. Generated once on first device pairing. Persisted only on user's devices.
- **SSK**: Ed25519. Generated client-side, signed by MSK. Used to sign every device leaf the user ever pairs. Bob's client validates a leaf via `leaf_signature → SSK_signature → MSK`.
- **USK**: Ed25519. Generated client-side, signed by MSK. Used only for *cross-user* verification — when Alice has verified Bob's MSK out-of-band (fingerprint, QR), she signs his MSK with her USK as a permanent attestation.
- **Recovery Key**: Optional. A passphrase-derived KEK (Argon2id, recommended params: m=64 MiB, t=3, p=4) wrapping the MSK as XChaCha20-Poly1305 ciphertext. Stored on the user's IdP. The IdP cannot decrypt without the passphrase. Brute force is bounded by the passphrase strength × Argon2id cost.

### What the IdP signs

**Nothing.** The IdP issues no certificates, signs no user identities, and is not in any cryptographic trust chain. It serves keys; clients verify them.

(Compare to OIDC tokens, which the IdP *does* sign — those bind `actor_uri` to a session. They never bind `actor_uri` to a long-term encryption identity.)

### How Bob trusts that an MSK belongs to Alice

1. **First contact (TOFU)**: Bob's client fetches Alice's MSK from her IdP's key directory the first time it adds her to a conversation. It pins her MSK fingerprint locally. No cryptographic guarantee — the IdP could lie at this moment. Affirmative defence: optional out-of-band fingerprint verification.
2. **Subsequent contact**: client compares fetched MSK fingerprint to the pinned one. Match → silent. Mismatch → non-dismissible "Alice's identity changed — verify before continuing" warning. Sends are blocked until the user explicitly accepts the new key.
3. **Out-of-band verification**: Bob and Alice compare a 60-character base32 fingerprint of each other's MSK in person, by phone, by QR, or any side channel. On confirm, Bob's USK signs Alice's MSK as a permanent attestation. Future identity changes are still warned, but past verified state is preserved as provenance.

### Account recovery

| Scenario | Outcome |
|---|---|
| User loses one device, has at least one other | Open the surviving device → "Revoke lost device" → an MLS Update commit removes the lost leaf from every group. PCS recovers within that commit. |
| User loses all devices, has Recovery Key | Re-authenticate via OIDC on a new device → fetch wrapped MSK from IdP → enter passphrase → decrypt → restore identity. New device leaf joins all groups via standard re-add. |
| User loses all devices, did not opt into Recovery Key | Past conversations are unrecoverable. User must register a new MSK. Contacts will see "Alice's identity changed" and re-verify. |

## 3. Key directory

### Schema additions

```sql
-- Long-term per-user identity keys (MSK + SSK + USK fingerprints).
-- Public-key material only; private keys live exclusively on user devices.
CREATE TABLE user_identity_keys (
    user_id            UUID PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
    msk_public         BYTEA NOT NULL,     -- Ed25519 public key
    ssk_public         BYTEA NOT NULL,
    ssk_signature      BYTEA NOT NULL,     -- SSK signed by MSK
    usk_public         BYTEA NOT NULL,
    usk_signature      BYTEA NOT NULL,     -- USK signed by MSK
    published_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
    rotated_at         TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- KeyPackages — one bundle per device-leaf, consumed once per group add.
-- Devices replenish their KeyPackage stash on a schedule.
CREATE TABLE key_packages (
    id                 UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id            UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    device_id          UUID NOT NULL,           -- client-generated, opaque to server
    key_package        BYTEA NOT NULL,          -- TLS-encoded MLS KeyPackage struct
    expires_at         TIMESTAMPTZ NOT NULL,
    consumed_at        TIMESTAMPTZ,             -- NULL = available; set when handed out
    created_at         TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_key_packages_available
    ON key_packages (user_id, expires_at)
    WHERE consumed_at IS NULL;

-- Wrapped MSK for opt-in account recovery.
-- IdP cannot decrypt without the user's passphrase.
CREATE TABLE recovery_blobs (
    user_id            UUID PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
    wrapped_msk        BYTEA NOT NULL,          -- XChaCha20-Poly1305 ciphertext of MSK
    salt               BYTEA NOT NULL,          -- 32 bytes, unique per user
    argon2_params      JSONB NOT NULL,          -- { m_kib, t, p } for parameter migration
    created_at         TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at         TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

### Endpoints

| Endpoint | Auth | Purpose |
|---|---|---|
| `POST /api/keys/identity` | Bearer | Publish or rotate the caller's MSK + SSK + USK fingerprints (with their self-signatures). One row per user, replaced on rotation. |
| `GET /api/keys/identity/:actor_uri` | Bearer (local user) **or** HTTP-Sig (peer IdP) | Fetch a user's published identity public keys. Used for first-contact pinning + identity-change detection. |
| `POST /api/keys/packages` | Bearer | Upload a batch of KeyPackages (typically 20–50 at a time) for one of the caller's devices. |
| `POST /api/keys/packages/claim` | Bearer (local user adding) **or** HTTP-Sig (peer IdP adding) | Atomically reserve and return one KeyPackage for `actor_uri`. `device_id` is optional — when omitted (the typical cross-IdP case) the server picks any device of `actor_uri` that has spare KeyPackages and returns the chosen `device_id`. Server marks `consumed_at = now()`. **Bearer + remote `actor_uri`**: the local IdP proxies the request to the target's IdP via HTTP-Sig (the local user's bearer becomes the local IdP's signed request to the peer; cross-IdP callers don't know peer device IDs, so this proxy hop is mandatory). **Peer + remote `actor_uri`**: rejected, to prevent proxy chains. Either auth + local target: existing local lookup. If no unexpired KeyPackages remain, `503` and the caller retries — peer is expected to refresh its stash. |
| `GET /api/keys/packages/status` | Bearer | Returns each device's available KeyPackage count + expiry distribution; client refills when low. |
| `PUT /api/keys/recovery` | Bearer | Upload a wrapped-MSK blob + salt + Argon2id params. |
| `GET /api/keys/recovery` | Bearer | Fetch the wrapped blob for offline decryption. |
| `DELETE /api/keys/recovery` | Bearer | Opt out (or rotate). |

### Rotation policy

- **MSK**: rotated only on explicit "all devices compromised, escape hatch" flow. Every contact sees a "Bob's identity changed" warning. Should be rare — once a year or never.
- **SSK / USK**: rotated when a device leaf is lost. New SSK signed by the same MSK; old SSK fingerprint kept on file for retroactive validation of historical signatures.
- **KeyPackages**: each one is single-use (consumed on group add). Each device keeps a stash with a **cap of 100** server-side; the client tops up in the background whenever its available count drops **below 20**. KeyPackages have a `lifetime` field of **30 days**; expired rows are garbage-collected by the existing orphan-sweep task. All three values are env-tunable for operators.

### Federation

Peer-IdP fetches use HTTP Signatures (the same scheme already in place for ActivityPub delivery). The signature's `keyId` identifies the requesting IdP; the responding IdP just serves the requested rows. No additional auth state needed.

## 4. Group lifecycle

### Mapping MLS to existing schema

| MLS concept | Pina'i mapping |
|---|---|
| Group | One row in `conversations` (kind = `'dm'` for 2-member, `'group'` for ≥3). The MLS group is identified by `conversation_id`. |
| Member (user-level) | One row in `conversation_members` (`actor_uri`). |
| Member (leaf-level) | Each device the user has paired = one leaf in the MLS group tree. The server does **not** store leaf-to-device mapping — that's MLS group state, which lives client-side. |
| Welcome | Stored in `mls_welcomes` table (see below) until the new device fetches it. |
| Commit | Stored in `mls_commits` table; clients pull missed commits on reconnect. |
| Epoch | Implicit in commit ordering. |
| Application message | One row in `direct_messages` with `mls_ciphertext` populated, `content` NULL. |

### New tables

```sql
-- Per-group MLS state held by the Delivery Service (this IdP, when this is
-- the conversation's home). Body is opaque to the server.
CREATE TABLE mls_commits (
    id                  UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    conversation_id     UUID NOT NULL REFERENCES conversations(id) ON DELETE CASCADE,
    epoch               BIGINT NOT NULL,
    commit_blob         BYTEA NOT NULL,          -- TLS-encoded MLS Commit message
    proposer_actor_uri  TEXT NOT NULL,           -- whose device proposed it
    created_at          TIMESTAMPTZ NOT NULL DEFAULT now(),

    UNIQUE (conversation_id, epoch)
);

CREATE INDEX idx_mls_commits_catchup
    ON mls_commits (conversation_id, epoch);

-- Welcome bundles for offline device add events. Consumed when the recipient
-- device fetches it.
CREATE TABLE mls_welcomes (
    id                   UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    recipient_user_id    UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    recipient_device_id  UUID NOT NULL,           -- targeted leaf
    welcome_blob         BYTEA NOT NULL,          -- TLS-encoded MLS Welcome message
    conversation_id      UUID NOT NULL,           -- redundant; helps routing
    created_at           TIMESTAMPTZ NOT NULL DEFAULT now(),
    consumed_at          TIMESTAMPTZ
);
```

### DS assignment

The DS for a conversation is the IdP that hosts the conversation row. For DMs that row is minted at **friendship-accept** time on the accepter's IdP (see § 1 in `01-identity-federation.md`), and the conversation_id is propagated to the requester's IdP either via a WS event (local) or in the AP `Accept{Follow}` activity's `conversationId` field (cross-IdP). The MLS `group_id` IS the conversation_id — `mls.createGroup(conversation_id)` runs once on the first send into the conversation, both sides agree on the id from the start, and there is no client-side UUID minting on first-message-send. Cross-IdP messages travel via existing ActivityPub transport; commits and welcomes travel inside the same `Create{Note}` envelope (see § 5).

The DS's responsibilities, opaque-to-content:
- Assign and serve a strict total order of commits per group.
- Reject any commit whose `epoch` is already taken (concurrent-commit conflict — see below).
- Hand out fresh KeyPackages on Add.
- Store Welcomes until the targeted device fetches them.

### Concurrent commit handling

Two members can race to commit at the same epoch. MLS expects the DS to break the tie. Strategy:

- DS accepts the **first** commit it durably stores (`UNIQUE(conversation_id, epoch)` enforces it).
- The losing commit's proposer receives `409 Conflict` with the winning commit's body. Their client applies it locally, then re-proposes their own change at the new epoch. (Standard MLS recovery.)

Because we don't have a `federation_queue` and AP delivery is best-effort, the DS may sometimes serialize commits that arrive over WS faster than commits that arrive via AP — that's acceptable and the client handles it.

### Endpoints

| Endpoint | Auth | Purpose |
|---|---|---|
| `POST /api/mls/groups/:conversation_id/commits` | Bearer (member-gated) | Submit a Commit. Server appends if `epoch` is the next one; else `409` with the conflicting commit. **First-message lazy-create**: when no `conversation_members` row exists yet *and* the proposed `epoch ≤ 1`, the server lazy-creates the conversation as a DM with the proposer as the sole initial member. After the friendship-creates-conversation refactor the conversation row is created at `set_status('accepted')` time, so this path is no longer load-bearing — it stays as defense-in-depth against the (unlikely) case where MLS bootstrap fires before the conversation row has materialized client-side. Commits at `epoch > 1` against a missing conversation still 404. |
| `GET /api/mls/groups/:conversation_id/commits?since=:epoch` | Bearer (member-gated) | Pull missed commits on reconnect / multi-device sync. |
| `GET /api/mls/welcomes?device_id=:uuid` | Bearer | Pull pending Welcomes targeted at one of the caller's devices. Server marks them `consumed_at` on read; per-device parameter keeps multi-device users from racing each other. |
| `POST /api/mls/welcomes` | Bearer | Hand a Welcome bundle to the sender's IdP for delivery. The IdP routes based on `recipient_actor_uri`: **local** → `mls_welcomes` insert + `MlsWelcomeReady` WS event, also adds `recipient_actor_uri` to `conversation_members` (idempotent) so the subsequent `POST /api/dm` finds an existing 2-member DM via `find_dm_between`; **remote** → signed AP `Create{Note}` with `mlsKind: welcome` to the recipient IdP's inbox, *also* adds the recipient to our own local `conversation_members` so the local DM lookup reuses the same `conversation_id`. The client never branches on local-vs-remote — it always hands the welcome to its own IdP. |

### Add / Remove flows

**Add (existing conversation, by the device that proposes the commit)**
1. Proposer's client fetches a fresh KeyPackage for the new member via `POST /api/keys/packages/claim`. For a remote `actor_uri` the proposer's own IdP transparently proxies via HTTP-Sig to the target's IdP (browsers can't sign HTTP-Sig themselves). For same-user multi-device the client can still pin a specific `device_id`.
2. Builds an Add proposal + Commit.
3. POSTs the Commit to the DS endpoint above. If this is the founder's first commit, the server lazy-creates the DM conversation (see endpoint description).
4. Builds a Welcome targeted at the new device's leaf.
5. POSTs the Welcome to `POST /api/mls/welcomes`. The IdP routes — local recipients get a row + WS event, remote recipients get an AP `Create{Note}` (see § 5). On the local path the recipient is also added to `conversation_members` so the subsequent `POST /api/dm` reuses the same conversation row.

**Remove**
1. A remaining member's client builds a Remove proposal + Commit.
2. Submits to the DS. From the next epoch on, the removed leaf can no longer derive group keys.
3. (Optional) The removed user's local IdP can mark `conversation_members.left_at = now()` for hygiene; server doesn't strictly need this since MLS already enforced removal cryptographically.

**Update**
1. Periodic, or on suspected device compromise.
2. Device generates a new leaf key, signs it with SSK, builds an Update proposal + Commit.
3. Submits to the DS. PCS recovers within that epoch.

## 5. Wire format

### Schema changes to `direct_messages`

```sql
ALTER TABLE direct_messages
    ALTER COLUMN content DROP NOT NULL,         -- now NULL for E2EE rows
    ADD COLUMN mls_ciphertext BYTEA,            -- TLS-encoded MLSMessage
    ADD CONSTRAINT direct_messages_payload_check
        CHECK (mls_ciphertext IS NOT NULL);     -- mandatory under § 1 ("C")
```

The pre-existing columns we keep, all server-visible:
- `id`, `conversation_id`, `sender_actor_uri` (which user — leaf identity is inside the ciphertext)
- `activity_uri` (cross-instance correlation)
- `reply_to_id` (server uses for routing — see § 6)
- `created_at`, `edited_at`, `deleted_at`

The pre-existing column we drop semantically:
- `content` is always NULL for new rows. We don't drop the column outright in case future variants of opaque payloads need it.

### ActivityPub envelope

MLS payloads (commits, welcomes, application messages) ride inside a `Create{Note}` activity, distinguished by the Note's `mediaType`:

```json
{
  "@context": "https://www.w3.org/ns/activitystreams",
  "type": "Create",
  "actor": "https://idp.alice.com/users/alice_xK9mP",
  "object": {
    "type": "Note",
    "id": "https://idp.alice.com/users/alice_xK9mP/activities/<uuid>",
    "mediaType": "application/mls",
    "context": "<conversation_id>",
    "content": "<base64(MLSMessage)>"
  }
}
```

`MLSMessage` is the union type from RFC 9420 — covers Commits, Welcomes, and Application messages with a `wire_format` discriminator. The inbox handler dispatches on the discriminator after base64-decoding.

Peer IdPs that don't recognise `application/mls` reject the activity (existing inbox behaviour for unknown mediaTypes).

### WebSocket envelope

Local delivery (same IdP) uses the existing `WsEvent::NewDm` shape, with one new field:

```rust
pub struct DmPayload {
    // … existing fields …
    /// Base64-encoded MLSMessage when this is an E2EE conversation.
    pub mls_ciphertext: Option<String>,
}
```

The `content` field stays in the type for now (NULL on the wire for E2EE messages) so the migration path doesn't churn the protocol shape.

## 6. Application messages

### What's encrypted inside the MLS payload

The MLS application-message body is a TLS-encoded struct of the form:

```
struct ApplicationMessage {
    uint8 version = 1;
    ApplicationKind kind;     // text | reaction | edit | reply_meta | system
    opaque body<0..2^24-1>;   // kind-dependent
}
```

| `kind` | `body` contents | Replaces |
|---|---|---|
| `text` | UTF-8 message text | The current `direct_messages.content` for plain messages |
| `reaction` | `{ target_message_id: UUID, emoji: string, op: "add" \| "remove" }` | The `message_reactions` table for E2EE conversations (see below) |
| `edit` | `{ target_message_id: UUID, new_text: string }` | The current edit flow's plaintext content |
| `reply_meta` | `{ target_message_id: UUID, preview_text: string, preview_sender: string }` | The plaintext `reply_to_content` / `reply_to_sender` preview fields |
| `system` | `{ event: "joined" \| "left" \| "renamed" \| …, params: …}` | Reserved for client-rendered system messages |

### Reactions

For E2EE conversations the `message_reactions` table is **not used**. Reactions are application messages of `kind = reaction`, encrypted in the MLS stream. Each client maintains its own reaction state by replaying the stream.

This loses one server-side feature — the conversation list query can no longer include "did anyone react to my last message?" hints. Clients must compute that locally. Acceptable for E2EE.

### Replies

`reply_to_id` stays plaintext on the row — the server still needs it to thread messages and to soft-delete-cascade behaviour. But the **preview** (`reply_to_content`, `reply_to_sender`) currently leaked to the server is moved into the MLS body as a `reply_meta` application message piggy-backed onto the reply itself. Clients render the preview from that.

### Edits

`edited_at` stays a plaintext timestamp on the row (the server uses it for sort order). The new content travels as a `kind = edit` application message in the MLS stream, referencing the original message by ID. Clients track the latest edit per `target_message_id`.

The PATCH `/api/dm/:message_id/edit` endpoint becomes a thin wrapper that:
1. Updates `direct_messages.edited_at`.
2. Forwards the edit's MLSCiphertext blob exactly like a new message (it travels through the same pipeline).

### Server-side soft delete

Unchanged — `deleted_at` is plaintext metadata and the server already uses it. E2EE doesn't change it.

## 7. Attachment encryption

### Flow

1. Client picks a file.
2. Client generates a random 32-byte AES-256 key + 12-byte nonce.
3. Client encrypts the file bytes with AES-256-GCM. AAD = the attachment's UUID (which the client also generates).
4. Client uploads the **ciphertext** via the existing `POST /api/attachments` endpoint. Server stores opaque bytes; nothing about its API changes.
5. Client sends a DM whose MLS application body includes:
   ```
   {
     kind: "text",
     body: <utf-8 message text>,
     attachments: [
       { id: <uuid>, key: <32 bytes>, nonce: <12 bytes>,
         original_filename: "...", mime_type: "...", byte_size: ... }
     ]
   }
   ```
6. Recipient decrypts the MLS body, fetches ciphertext via the existing `GET /api/attachments/:id/blob?token=...` flow (already streams through the IdP — no other change needed), decrypts locally with the embedded key + nonce.

### Schema changes to `message_attachments`

```sql
ALTER TABLE message_attachments
    -- These were server-visible plaintext; now they're opaque-to-server
    -- (still recorded for orphan-sweep audit and as opaque size indicator,
    -- but the values are uploaded by the client as deliberate "decoy" or
    -- truncated values — see below).
    -- We do NOT drop them — clients send obscured values for backward shape compat.
    ALTER COLUMN mime_type SET DEFAULT 'application/octet-stream',
    ALTER COLUMN original_filename SET DEFAULT 'encrypted',
    ALTER COLUMN byte_size SET NOT NULL;     -- byte_size is the *ciphertext* size,
                                              -- which leaks file-size class anyway,
                                              -- so it stays as-is
```

What this means in practice:
- `original_filename` is sent as `"encrypted"` (or the literal `id` as a stable placeholder) by the client; the real filename lives in the MLS body.
- `mime_type` is sent as `application/octet-stream`; the real MIME lives in the MLS body.
- `byte_size` reflects the ciphertext size, which is `original_size + 16` (GCM tag). The size class leaks — accepted as standard E2EE trade-off.

### Per-attachment key lifecycle

Keys are ephemeral, never persisted server-side, never reused. Each new send generates fresh material. There is no key rotation problem because the key is bound to a single attachment.

### Federation

`message_attachments.remote_origin_url` and the existing peer-IdP `/api/attachments/:id/content` flow continue unchanged — peer IdPs stream the ciphertext bytes through (see [`03-direct-messages.md § 9`](./03-direct-messages.md)). The decryption key only travels inside the encrypted MLS body, never on a federation control plane.

## 8. Multi-device

### Pairing flow

Existing device → new device, in person or screen-share:

1. New device generates: device key pair, device ID (UUID).
2. Existing device shows a QR encoding `{ msk_public, ssk_pair_token, paired_at }`.
3. New device scans the QR, derives a session via PAKE (CPace/SPAKE2 — TBD; library available).
4. Existing device sends MSK private + SSK private over the PAKE channel.
5. New device signs its leaf key with SSK and uploads to its IdP via `POST /api/keys/packages` (and identity row via `POST /api/keys/identity` — but the identity is already published, so this is a no-op for MSK).
6. For every group the user is in: an existing device proposes `Add(new_device_leaf)` + Commit, and sends a Welcome targeted at the new leaf.

When a user has only one device, pairing requires no Welcome propagation since there's no group state to inherit yet (or the user re-runs through groups manually).

### Lost-device revocation

1. User opens a surviving device → Settings → "Revoke other device".
2. Surviving device propagates an MLS Update commit per group, removing the lost leaf.
3. Surviving device deletes the MSK passphrase wrap on the IdP if Recovery Key was tied to that device's ownership (it isn't, but a paranoid mode could rotate the wrap).
4. Optional: revoke any consumed-but-unfetched Welcomes targeted at the lost device by writing `consumed_at = now()`.

### Adding a device to an existing user with N groups

Cost: N commits (one per group), each O(log group_size). For a typical user in ~50 groups, that's ~50 commits within seconds of pairing. Acceptable.

## 9. Recovery Key

### Design

Opt-in at registration (or anytime via Settings). User chooses a passphrase. Client:

1. Generates a 32-byte salt.
2. Derives a KEK using Argon2id (default params: m = 64 MiB, t = 3, p = 4).
3. Encrypts the MSK private bytes with XChaCha20-Poly1305 using the KEK and a random 24-byte nonce. AAD = a domain string `"pinai/recovery-msk/v1"`.
4. Uploads `{ wrapped_msk: <ciphertext>, salt, argon2_params }` to `PUT /api/keys/recovery`.

Recovery flow:

1. New device authenticates via OIDC (re-establishes "I am alice@idp.alice.com").
2. Fetches the wrapped blob via `GET /api/keys/recovery`.
3. Prompts for passphrase. Derives KEK locally. Decrypts.
4. Restores MSK locally. Generates fresh device leaf, signs with restored SSK.
5. Pairs into all groups via the standard add flow.

### Security properties

- **IdP cannot decrypt.** The KEK is never on the server; only the wrapped ciphertext is.
- **Brute force is offline + bounded.** An attacker who exfiltrates the wrapped blob from a database breach must run Argon2id × passphrase entropy. With recommended params and a 12+ character random passphrase, this is computationally expensive to the point of impracticality at scale.
- **No key escrow.** No second party can recover.
- **Failure modes that the user accepts when opting in:**
  - Forgotten passphrase = lost identity (same as the no-Recovery-Key case).
  - Compromised passphrase + IdP DB breach = full identity compromise. Mitigation: pick a strong passphrase.

### Opt-out

`DELETE /api/keys/recovery` removes the wrapped blob. From that point on, "lose all devices" = "lose history".

---

## 10. Migration

Pina'i is **pre-deployment**. All conversations are E2EE from the day this lands. There is no plaintext-to-encrypted migration path; the `content` column on existing development databases (if any) is dropped or the table is recreated.

## 11. UI / UX requirements imposed by the protocol

Items the spec requires the client to implement for the protocol's security properties to actually hold:

| Requirement | Why |
|---|---|
| First-contact TOFU pinning of every contact's MSK fingerprint | Otherwise an IdP-supplied substitution is undetectable |
| Non-dismissible "identity changed" warning on MSK rotation, blocking sends until acknowledged | Otherwise retroactive MITM is undetectable |
| Out-of-band fingerprint verification UI (60-char base32 + QR + emoji-mapping option) | Otherwise users can never escape pure TOFU |
| Recovery Key onboarding screen with strength meter and clear "if you lose this passphrase, your account is unrecoverable" copy | Otherwise users opt in casually and lose data |
| "Devices" management screen listing every paired device with leaf fingerprint, last-seen, "Revoke" button | Otherwise lost-device recovery is impossible |
| Pairing QR display + scanner | Otherwise new devices can't join |
| Visible-but-not-blocking "encrypted" badge on every conversation | UX legibility — users should know the protection they have |

## 12. Out of scope (deferred)

- **Sealed sender / metadata privacy.** Server still sees membership, ordering, sender device per message, timestamps. Reducing this requires anonymous credentials or padded delivery; large additional design surface.
- **Cover traffic / traffic-pattern analysis resistance.** Not addressed.
- **MLS group catch-up beyond the commit log retention window.** The DS keeps commits indefinitely today; if storage pressure forces eviction later, define a snapshot-and-restart protocol then.
- **Migration from MLS v1 to a future MLS v2.** Per the RFC's extension story; not yet relevant.
- **Cross-DS group migration** (a group's conversation_id moving from one IdP to another). No use case yet; would require a coordinated handoff.
- **Federated key-package discovery for users who haven't been a contact yet** (i.e. truly "addressless" first contact). Today peer IdPs only fetch KeyPackages for users their local users explicitly contact.

## 13. Open questions / known issues

- **Concurrent-commit storms.** If two devices rapidly propose conflicting commits, both lose alternately and re-propose. Bounded by client backoff. Worth load-testing at implementation time.
- **KeyPackage exhaustion.** A misbehaving peer IdP could repeatedly claim KeyPackages for a user without ever Welcoming them, draining the stash. Mitigation: rate-limit `claim` per requester; alert the user to refill if their available count drops below a threshold.
- **First-message latency under cross-IdP add.** Adding a remote user requires a synchronous fetch of their KeyPackage via HTTP-Sig; if their IdP is slow, the conversation creation UX feels sluggish. Mitigation: client shows "Adding Bob…" optimistically, retries on failure.
- **Argon2id parameter migration.** As hardware improves, recommended params will rise. The `argon2_params` column allows the client to detect and re-wrap on the next opt-in. Need a clear rotation prompt at appropriate time.
